# Guidelines for working on ScrambledTreeBuilder

ScrambledTreeBuilder is an R package that reads the per-pair YAML statistics
produced by the `pairgenomealign` and GenomicBreaks pipelines, builds a
distance tree of the genomes, and projects pairwise statistics (scrambling
index, percent difference, …) onto the tree's internal nodes (most recent
common ancestors).  The vignette (`vignettes/ScrambledTreeBuilder.Rmd`) walks
through the whole pipeline and is the best overview.

## Tests catch regressions, examples document

The two have separate jobs.  Do not use one for the other.

**`tests/testthat/`** is the regression net.

- One test file per source file: `R/foo.R` → `tests/testthat/test-foo.R`.
- Check **values**, not just that something runs.  Prefer
  `expect_equal(result, expected)` against values computed independently
  (by hand, or with a simpler base R expression) over
  `expect_true(is.data.frame(x))`.
- Do not use snapshot tests for values that an `expect_*` call can state
  directly.  Snapshots silently record whatever the code returns, including
  wrong results.
- Use the lazy-loaded example data (`Halo_DF`, `Halo_PercentDiff`,
  `Halo_Tree`, `Halo_FocalClades`, `oikData`) and the helpers in
  `tests/testthat/helper-data.R`.  When those don't fit, build a small
  synthetic input in the test file; use `set.seed()` if it is random.
- Write temporary files under `withr::local_tempdir()`.
- Test plots through their data, not their pixels: class, number of layers,
  `ggplot2::layer_data()`, or for `pheatmap` the `gtable` grobs.  Pass
  `silent = TRUE` to `treeHeatMap()`.
- Cover the error paths and options of each function (`expect_error()`,
  `expect_warning()` with a message pattern).
- Internal functions can be tested with `ScrambledTreeBuilder:::fun()`.
- The whole suite should run in seconds.  Keep bootstrap replicates and
  similar loops small.

**`@examples`** are user documentation.

- Show typical usage in a few short lines on the example data.  Each
  example should teach something a user would do.
- Edge cases, error conditions, and every combination of options belong in
  tests, not examples.
- Internal (non-exported) functions have no examples.
- No commented-out examples: if it is worth showing, make it run.
- Examples must not depend on packages in `Suggests` unless guarded with
  `if (requireNamespace(...))`.

## Known bugs

When you find a bug that you are not fixing right away, write the test that
describes the **correct** behaviour and skip it:

```r
test_that("recordClades() computes missing MRCAs", {
  skip("Known bug: recordClades() passes the clades instead of a tree to recordAncestor().")
  ...
})
```

The suite stays green, `devtools::test()` lists the known bugs under
"Skipped", and fixing a bug means deleting its `skip()` line and making the
test pass.  Never write a test that asserts the buggy behaviour.

## Fixing bugs and adding features

1. Start from a failing test (or un-skip a known-bug test).
2. Make the change.
3. Run `devtools::test()`; if the change touches documentation, also run
   `roxygen2::roxygenise()` and `devtools::run_examples()`.
4. Add a line to `NEWS.md` under the development version heading for any
   user-visible change.

## Code conventions

- Argument names: `pairwise_data` for results data frames (one pair of
  genomes per row, from `formatStats()`), `pairwise_matrix` for square
  species × species matrices (from `makeMatrix()`), `species_tree` or `tree`
  for `stbTree` objects (from `makeTidyTree()`).
- Classes use S7 (`stbTree`, `FocalClade`, `FocalCladeList`).  Methods are
  registered in `.onLoad()` (`R/zzz.R`).
- Documentation is roxygen2 with Markdown.  Never edit `man/*.Rd` or
  `NAMESPACE` by hand: edit the roxygen comments and run
  `roxygen2::roxygenise()`.  If roxygen2 itself is upgraded, commit the
  resulting reformatting separately from content changes.
- Import functions from other packages with `@importFrom pkg fun` in the
  roxygen block of the function that uses them, and call them without the
  `pkg::` prefix.  Older code still uses prefixes; convert it when you touch
  it.  Packages in `Suggests` are the exception: call them with `pkg::` after
  checking `requireNamespace()`.
- Functions written from scratch by an AI agent get an `@author` tag naming
  the model, for example `@author Claude Opus 5.5 (Anthropic)`.  Do not add
  it to existing functions that you only modify.
- Match the surrounding style: base R pipe `|>`, `\(x)` lambdas, and
  `.data$col` inside dplyr verbs and `aes()`.

## Example data

- `data/*.rda` are generated by the scripts in `data-raw/`.  Edit the script,
  re-run it from the package root, and commit the script and the `.rda`
  together.
- `tests/testthat/test-data.R` checks that the example objects are
  consistent with each other and with the package functions.  If it fails
  after a code change, the data may need regenerating.

## Commits

- Keep commits focused: tests, documentation, generated files and
  behaviour changes in separate commits where practical.  In particular,
  when a new function adds itself to the `@family` lists of other help
  pages, commit those regenerated `man/` files separately from the
  function.
- Commit messages: a short summary line, then a body explaining why when it
  is not obvious.
